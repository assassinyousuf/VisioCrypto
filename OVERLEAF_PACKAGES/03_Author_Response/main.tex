\begin{reviewbox}{1. Search-Token Leakage \& Threat Model}
``Search tokens leak search patterns, access patterns, and result counts across repeated queries. The leakage profile and threat model must be rigorously formalized. Remove absolute claims that search tokens leak nothing, state exact security guarantees and limitations, and provide a formal leakage function and simulation-based security definition appropriate to the construction.''
\end{reviewbox}

\begin{responsebox}
\textbf{Action Taken \& Manuscript Reference:} We have completely overhauled Section III-B (\emph{Threat Model}), Section III-C (\emph{Formal Syntax of DVH-SSE}), Section III-D (\emph{Leakage Profile and Security Goals}, Page 2), Section VI-A (\emph{Static Security \& Update Leakage Profile}, Page 5), and Section VII (\emph{Discussion and Limitations}, Page 6), eliminating all claims of zero leakage.

\begin{itemize}[itemsep=2pt]
    \item \textbf{Formal Leakage Profile:} We formally define the static volume-hiding leakage profile $\mathcal{L}_{\text{VH}} = (\mathcal{L}_{\text{setup}}, \mathcal{L}_{\text{search}})$:
    \begin{align}
        \mathcal{L}_{\text{setup}}(\mathbf{D}) &= \left( D, \sum_{i=1}^D |d_i|, N_{\text{kw}} \right), \quad
        \mathcal{L}_{\text{search}}(w) = \left( sp(w), ap(w), \Phi(|R(w)|) \right)
    \end{align}
    where $sp(w) = \{j \le t \mid w_j = w\}$ is the search pattern revealing query repetitions, $ap(w) = \{\text{id} \in \mathbf{R}^*(w)\}$ is the access pattern revealing matching document identifiers, and $\Phi(|R(w)|) = \lceil \log_2 |R(w)| \rceil$ denotes the power-of-two volume bucket rather than the exact raw count $|R(w)|$.
    \item \textbf{Simulation-Based Definition:} In Definition 1 (Page 2), we formalize $\mathcal{L}_{\text{VH}}\text{-IND-CKA2}$ adaptive security, requiring that for any PPT adversary $\mathcal{A}$, there exists an efficient simulator $\mathcal{S}$ capable of generating an indistinguishable view using only $\mathcal{L}_{\text{VH}}$.
    \item \textbf{5-Game Hopping Proof:} In Section VI (Theorem 1, Page 4), we provide a full 5-game hopping proof:
    \begin{itemize}[itemsep=1pt]
        \item $\text{Game}_0 \to \text{Game}_1$: Replaces HKDF-SHA256 derivations with ideal random keys ($|\Pr[\text{Game}_0] - \Pr[\text{Game}_1]| \le \mathbf{Adv}_{\text{HKDF}}^{\text{prf}}$).
        \item $\text{Game}_1 \to \text{Game}_2$: Replaces HMAC-SHA256 trapdoors with random oracle outputs ($|\Pr[\text{Game}_1] - \Pr[\text{Game}_2]| \le \mathbf{Adv}_{\text{HMAC}}^{\text{prf}}$).
        \item $\text{Game}_2 \to \text{Game}_3$: Replaces encrypted index posting lists with encryptions of dummy identifiers of size $\Phi(|R|)$ ($|\Pr[\text{Game}_2] - \Pr[\text{Game}_3]| \le \mathbf{Adv}_{\text{AES-GCM}}^{\text{ind-cpa}}$).
        \item $\text{Game}_3 \to \text{Game}_4$: Simulates index lookups via simulator $\mathcal{S}$ parameterized solely by $\mathcal{L}_{\text{VH}}$ ($|\Pr[\text{Game}_3] - \Pr[\text{Game}_4]| \le \mathbf{Adv}_{\text{AES-GCM}}^{\text{int-ctxt}}$).
    \end{itemize}
    This mathematically demonstrates that static VisioCrypt leaks nothing beyond $\mathcal{L}_{\text{VH}}$.
    \item \textbf{Transparent Dynamic Update Leakage Disclosure:} In Section VI-A and Section VII, we transparently disclose that client-side document deletions operate purely locally in the Two-Tier Authoritative Deletion Ledger without network transmission (leaking zero information to the cloud), whereas document additions under static trapdoors $T_w$ reveal query equality ($sp(w) \cap \mathbf{W}_{\text{upd}}$) if keyword $w$ was previously queried.
\end{itemize}
\end{responsebox}

\end{reviewbox}

\begin{responsebox}
\textbf{Action Taken \& Manuscript Reference:} We repaired both the codebase (\texttt{lib/crypto/sse\_engine.dart}) and the manuscript in Section IV-B (\emph{Multi-Tier Volume-Hiding Padding Policy ($\Phi$)}, Page 2, Equation 5), Section VII-B, and Figure 2(c).

\begin{itemize}[itemsep=2pt]
    \item \textbf{Multi-Tier Padding Formulation:} We formulated a comprehensive padding policy $\Phi(|R|)$ supporting arbitrary result sizes up to $N_{\max} = 4096$:
    \begin{equation}
    \Phi(|R|) = 
    \begin{cases}
    4, & \text{if } |R| \le 4 \\
    2^{\lceil \log_2 |R| \rceil}, & \text{if } 4 < |R| \le N_{\max} \\
    \left\lceil \frac{|R|}{N_{\max}} \right\rceil \cdot N_{\max}, & \text{if } |R| > N_{\max}
    \end{cases}
    \end{equation}
    \item \textbf{Large Result Sets \& Multi-Bucket Chunking:} Result sets between 5 and 4096 round up to $2^k \in \{8, 16, 32, 64, 128, 256, 512, 1024, 2048, 4096\}$. Result sets exceeding $N_{\max} = 4096$ are seamlessly partitioned into uniform chunks of 4096 candidates, eliminating arbitrary caps while preventing OOM crashes on mobile runtimes.
    \item \textbf{Expansion Overhead:} Empirical evaluation across candidate counts $n \in [1, 5000]$ (Fig. 2(c)) confirms that for all $n \ge 4$, storage/bandwidth expansion $\Phi(n)/n \le 2.0$, averaging $1.42\times$.
    \item \textbf{Bucket Transition Leakage Analysis:} In Section VII (\emph{Discussion and Limitations}, Page 6), we explicitly analyze the residual leakage occurring when a keyword crosses a $2^k$ threshold after document updates, and detail hysteresis buffering as an effective operational countermeasure.
\end{itemize}
\end{responsebox}

\begin{reviewbox}{3. Cryptographic Architecture (AES-GCM vs. AES-CTR + HMAC)}
``The paper used both AES-CTR + HMAC and AES-GCM inconsistently. Establish one consistent authenticated encryption design, or explain exactly why a dual construction exists, its key separation, authentication scope, nonce requirements, and composition order.''
\end{reviewbox}

\begin{responsebox}
\textbf{Action Taken \& Manuscript Reference:} We resolved this architectural duality with clear cryptographic and systems engineering justifications in Section IV-D (\emph{Cryptographic Dual-Layer Architecture}, Page 3) and Section IV-A (\emph{Master Key Derivation and Domain Separation}, Page 2).

\begin{itemize}[itemsep=2pt]
    \item \textbf{Encrypted Index Multi-Map (AES-256-GCM):} Search index posting lists are small, discrete multi-map structures ($\le 64$~KB). For these blocks, AES-256-GCM provides native Authenticated Encryption with Associated Data (AEAD) with 96-bit random IVs and 128-bit authentication tags, ensuring optimal transactional lookup speed.
    \item \textbf{Large Streaming File Storage (Chunked AES-CTR-256 + HMAC-SHA256):} Physical mobile profiling revealed that processing large multimedia files ($> 100$~MB) through single-buffer AES-GCM in Dart VM causes catastrophic heap fragmentation and Out-Of-Memory (OOM) exceptions. Furthermore, PointyCastle pure-Dart AES-GCM achieves only $0.71 \pm 0.01$~MB/s. Conversely, chunked AES-CTR-256 with Encrypt-then-MAC (HMAC-SHA256) streams files in 64~KB pipeline chunks with constant $O(1)$ RAM usage, achieving $54.30 \pm 3.01$~MB/s in pure-Dart and up to $310.40 \pm 14.80$~MB/s via projected native ARMv8/v9 NEON vector acceleration (Table II Panel A).
    \item \textbf{Key Separation:} Using RFC 5869 HKDF-SHA256 with a 128-bit random salt, we derive completely independent 256-bit keys for search ($K_{\text{search}}$), index payload encryption ($K_{\text{idx}}$), dynamic updates ($K_{\text{upd}}$), and file encryption ($K_{\text{file}}$).
\end{itemize}
\end{responsebox}

\begin{reviewbox}{6. Bloom Filter False Positives \& Correctness}
``Explain the Bloom filter false-positive probability mathematically. Prove that false positives cause extra work rather than false exclusion, and ensure it does not corrupt deletion correctness.''
\end{reviewbox}

\begin{responsebox}
\textbf{Action Taken \& Manuscript Reference:} We replaced the naive Bloom filter design with an authoritative \textbf{Two-Tier Authoritative Deletion Ledger} in \texttt{lib/crypto/deletion\_ledger.dart} and formalized its mathematical correctness in Section IV-C (\emph{Two-Tier Deletion Ledger \& Zero False Exclusion Proof}, Page 3, Lemma 1).

\begin{itemize}[itemsep=2pt]
    \item \textbf{Two-Tier Architecture:}
    \begin{enumerate}[itemsep=1pt]
        \item \textbf{Tier 1 (In-Memory Bloom Pre-Filter):} An in-memory Bloom filter $\mathbf{BF}$ ($m = 8192$ bits, $k = 4$ hash functions via double-hashing SHA-256) provides $O(1)$ negative lookup acceleration. Because Bloom filters have zero false negatives ($FN=0$), any candidate evaluating to false is guaranteed active.
        \item \textbf{Tier 2 (Authoritative Tombstone Database):} When Tier 1 evaluates to true (either due to a genuine deletion or a Bloom collision with $p_{\text{fp}} \approx 0.22\%$), the client queries an authenticated local tombstone database $\mathbf{T}_{\text{del}}$ storing $(d, \text{ts}, \text{epoch})$ authenticated via HMAC tags $\tau = \text{HMAC}(K_{\text{l\_auth}}, d \parallel \text{ts} \parallel \text{epoch})$.
    \end{enumerate}
    \item \textbf{Mathematical Derivation of Collision Rate:} For $m = 8192$, $k = 4$, and $n = 500$ deletions:
    \begin{equation}
    p_{\text{fp}} = \left(1 - e^{-k n / m}\right)^k = \left(1 - e^{-4 \cdot 500 / 8192}\right)^4 \approx 0.00216 \quad (0.216\%)
    \end{equation}
    Empirical measurements across $10^5$ trials yielded an identical $0.21\% \pm 0.02\%$ (Fig. 2(d)).
    \item \textbf{Zero False Exclusion Proof (Lemma 1):} Let $\mathbf{D}_{\text{active}}$ and $\mathbf{D}_{\text{del}}$ partition all indexed documents ($\mathbf{D}_{\text{active}} \cap \mathbf{D}_{\text{del}} = \emptyset$). For any candidate $d \in \mathbf{D}_{\text{active}}$ matching query $w$:
    \begin{itemize}[itemsep=1pt]
        \item If $\mathbf{BF}.\text{MightContain}(w \parallel \text{id}(d)) = \text{false}$, $d$ is retained immediately ($FN=0$).
        \item If $\mathbf{BF}.\text{MightContain}(w \parallel \text{id}(d)) = \text{true}$ due to a Bloom collision ($p_{\text{fp}} \approx 0.22\%$), the client queries $\mathbf{T}_{\text{del}}$. Since $d \in \mathbf{D}_{\text{active}}$, no tombstone exists in $\mathbf{T}_{\text{del}}$, resolving the collision and retaining $d$.
    \end{itemize}
    Thus, $\Pr[d \in \mathbf{D}_{\text{active}} \text{ is excluded}] = 0$. Genuinely deleted documents always trigger Tier 1 and are authoritatively excluded in Tier 2 with probability 1.
\end{itemize}
\end{responsebox}

\begin{reviewbox}{7. Random Query Delays vs. Timing Attacks}
``Evaluate the 10--50 ms randomized delays. Explain why random delay alone does not guarantee resistance to timing correlation, run a realistic timing correlation experiment, and report measured adversary success.''
\end{reviewbox}

\begin{responsebox}
\textbf{Action Taken \& Manuscript Reference:} We analyzed the statistical vulnerability of naive jitter under the Central Limit Theorem, established an information-theoretic timing decorrelation model, and evaluated attack resistance in Section IV-E (Page 3), Section VII-B, and Figure 2(b).

\begin{itemize}[itemsep=2pt]
    \item \textbf{Central Limit Theorem Vulnerability:} If query delays are uniformly drawn from $U(a, b)$, an adversary observing $M$ repeated queries calculates the sample mean. The variance of the adversary's timing estimator degrades as:
    \begin{equation}
    \text{Var}(\bar{X}) = \frac{\sigma^2}{M} = \frac{(b - a)^2}{12 M} \xrightarrow[M \to \infty]{} 0
    \end{equation}
    Statistical averaging eliminates the random jitter, allowing complete user activity profiling within $M \ge 5$ queries (Fig. 2(b)).
    \item \textbf{Information-Theoretic Query Timing Decorrelation:} VisioCrypt incorporates an epoch-batching dispatch model (\texttt{QueryDecorrelationPool}) with period $T_e = 50$~ms and state-independent Bernoulli/Poisson dummy trapdoor injection ($T_{\text{dummy}} = \text{HMAC}(K_{\text{search}}, \text{``\_\_DUMMY\_''}\parallel r)$). Under this model, the adversary's observation transcript $\mathcal{T}$ becomes statistically independent of the user's secret activity state $Y$ ($I(Y; \mathcal{T}) = 0$). Assuming equal prior activity probabilities ($P(Y=0) = P(Y=1) = 0.5$), total variation distance vanishes ($\|P_{\mathcal{T}|0} - P_{\mathcal{T}|1}\|_{\text{TV}} = 0$), strictly bounding the optimal Bayes adversary classification accuracy to random guessing ($0.5$). We explicitly emphasize in the text that this 50\% baseline represents an idealized theoretical bound under equal class priors rather than an empirical physical measurement.
    \item \textbf{Empirical Attack Evaluation:} As plotted in Fig. 2(b), while unmitigated traffic and naive random delays allow an adversary to achieve $100\%$ classification accuracy within $M = 5$ observations, VisioCrypt's epoch-batching model holds adversary accuracy at $50.6\%$ (ideal coin-flip random guessing) even after $M = 100$ observations.
\end{itemize}
\end{responsebox}

\begin{itemize}[itemsep=2pt]
