# VisioCrypt — Contribution-to-Evidence Matrix
**Paper ID:** 2015  
**Manuscript:** *VisioCrypt: A TEE-Anchored Client-Side Searchable Encryption Scheme with Dynamic Volume-Hiding Padding for Mobile Cloud Storage*  
**Venue:** IEEE ICCIT 2026  

This matrix directly answers Reviewer #2's critique regarding genuine scientific novelty by delineating what prior literature established, what VisioCrypt uniquely introduces, and the exact empirical implementation and security theorem supporting each claim.

| **1. Dynamic Client-Side Volume-Hiding SSE ($\text{DVH-SSE}$)** | SEAL [7] and Patel et al. [8] introduced volume hiding using oblivious RAM or multi-bucket binning on servers, incurring heavy client storage ($O(\text{polylog } N)$) and multi-round communication impractical for mobile. | A client-centric, multi-tiered geometric power-of-two padding policy $\Phi(R)$ ($n \in [1, 4096]$) combined with incremental versioned delta logging that hides exact candidate volume at an average bandwidth overhead of only $1.42\times$, operating over standard untrusted cloud object storage without server enclaves. | `lib/crypto/sse_engine.dart` (`computePaddedCapacity`, `padFileList`, `addDocumentDynamic`). | `timing_and_padding_experiments.py` (Fig. 2: Padded vs. Raw match counts up to $n=128$, evaluating expansion ratio $\Phi(n)/n \le 2.0$ for all $n \ge 4$). | Theorem 1 (Adaptive IND-CKA2 security proof in Section V bounding adversary advantage via Games 0–4 under leakage profile $\mathcal{L}_{\text{dyn-VH}}$). |
| **2. Client TEE Anchoring & Hardware Root Lifecycle** | Most enclave SSE works (Liu et al. [9], SGX-SE) deploy TEEs on the *untrusted cloud server*, requiring user trust in cloud provider hypervisors and exposing keys to cloud side-channel attacks. | Anchors the cryptographic root exclusively inside the *client mobile device* (ARM TrustZone / Android KeyMint / StrongBox) gated by biometric authorization (`BiometricPrompt` with `CryptoObject`), establishing strict domain-separated operational key derivation (HKDF-SHA256) where keys never leave client RAM. | `lib/screens/home_screen.dart` (`local_auth` biometric integration), `lib/crypto/hkdf.dart` (RFC 5869 domain separation). | Physical 4-device testbed evaluation across Snapdragon 8 Gen 3, Tensor G2, Exynos 2100, and Helio G80 (Table II). | Threat Model (Section III.B) defining physical device extraction and honest-but-curious cloud boundaries. |
| **3. Memory-Conscious Mobile Execution & Best-Effort Zeroization** | Academic SSE papers treat client devices as ideal Turing machines, ignoring runtime garbage collection (ART heap) where secret keys persist in volatile RAM for hundreds of seconds after cipher invocation. | Analyzes the Dart VM / Android ART memory lifecycle; executes cryptographic tasks in dedicated worker isolates; applies explicit in-place byte-array zeroization (`_zeroize`) immediately after cipher execution; documents the technical limits of garbage-collected language heaps with complete scientific honesty. | `lib/crypto/sse_engine.dart` (`_zeroize`), `lib/crypto/crypt_engine.dart` (`zeroize`), Listing 1 in revised manuscript. | Benchmark measuring RAM key persistence time in garbage-collected heap vs active memory wipe routines (Fig. 3). | Memory Hygiene Analysis (Section V.B) documenting mutable buffer clearing vs immutable string heap realities. |
| **4. Deletion Correctness via Negative Acceleration** | Naive Bloom filter deletions risk false positives that cause permanent, silent exclusion of legitimate matching documents from future search results. | Combines a compact in-memory Bloom filter ($m = 8192, k = 4$) with local state reconciliation: the filter is mathematically proven to serve solely as a *negative lookup accelerator*; positive filter matches trigger local document state verification, guaranteeing zero false document exclusions. | `lib/crypto/sse_engine.dart` (`SseBloomFilter.mightContain`, `searchIndex`). | `run_experiments.dart` empirical test of 10,000 negative lookups matching theoretical false-positive formula $p \approx (1 - e^{-kn/m})^k = 0.21\%$ (Fig. 4). | Correctness Proof (Section IV.C) proving that false positives cause bounded extra work rather than incorrect search results. |
| **5. Traffic Decorrelation & Query Batching** | Naive random delays (10–50 ms) fail against adversaries observing repeated queries due to Central Limit Theorem averaging ($\text{Var}(\bar{X}) = \sigma^2/M$). | Replaces ad-hoc random delays with `QueryDecorrelationPool`: batches queries into discrete 50 ms time epochs and injects pseudo-random dummy trapdoors (`__DUMMY_QUERY__`), strictly decoupling packet dispatch intervals from user typing dynamics. | `lib/crypto/sse_engine.dart` (`QueryDecorrelationPool.dispatchDecorrelatedBatch`). | Realistic timing correlation attack experiment (500 sessions, $M \in [1, 100]$) proving adversary accuracy drops from $100\%$ to $50.6\%$ (random guess) (Fig. 1). | Timing Security Model (Section IV.E) formalizing temporal indistinguishability over discrete dispatch epochs. |
| **6. Real-World Sub-Millisecond Mobile Performance** | Existing volume-hiding schemes incur multi-hundred-millisecond latencies on mobile devices due to cryptographic communication rounds. | Achieves measured sub-millisecond search resolution ($0.10 - 0.21$ ms on desktop; $0.23 - 1.48$ ms across 4 real mobile tiers) for indices up to 10,000 keywords, with symmetric file streaming hitting 310 MB/s on flagship mobile silicon. | `lib/crypto/benchmark.dart`, `run_experiments.dart`. | Empirical evaluation across 4 hardware tiers (Table III, Table IV, Fig. 3, Fig. 4) across $N = 100$ independent trials with 95% confidence intervals. | Complexity analysis proving optimal $O(1)$ index lookup time + $O(\Phi(|R|))$ decryption overhead. |
